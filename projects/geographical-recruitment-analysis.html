Geographical Inspection Recruitment Analysis

CMCS incurred additional costs when inspections required inspectors to travel beyond their normal territories. I developed a geospatial analysis system to identify concentrations of travel inspections and determine where local hiring could reduce future coverage costs. The initial analysis identified approximately $250,000 in projected annual savings opportunities.

Python Census Geocoding API Geospatial Clustering Leaflet.js openpyxl SQLite

The Problem

Paying a travel premium for coverage that already existed

Inspectors receive additional compensation when assignments require travel outside their normal service areas. Across the inspector network, some of this travel represented work that could potentially be covered more efficiently by existing local capacity or by establishing local coverage. CMCS had not previously had a systematic way to identify and quantify these geographic opportunities.

The Approach

Mapping and clustering travel inspections to find real hiring opportunities

I developed a pipeline that ingests current inspection data, geocodes inspection addresses, classifies inspections as local or travel relative to the assigned inspector, and clusters geographically concentrated travel inspections. The resulting clusters identify regions where the volume and distribution of travel work may justify local hiring. The system produces an interactive dashboard and an Excel report suitable for operational review.

Ingest inspection data → Geocode → Classify (Local / Travel) → Cluster (population-aware) → Dashboard + hiring report

Technical Implementation

A three-map dashboard, plus a hiring recommendation report

Every run produces one self-contained HTML dashboard with three interactive maps, and one Excel report:

Inspector Ranges

  • Maps every inspector alongside their inspections, classifying each one by whether it required travel, whether another inspector was already working nearby when it did, and whether it has already been completed or is still planned for later in the year. This was the first view of the inspector network laid out geographically rather than distributed across spreadsheets.

Inspector Ranges — 116 inspectors mapped with their inspection locations and classifications

Analysis Clusters

  • Clusters every travel inspection for the year that is geographically concentrated enough to represent a meaningful inefficiency. Clusters can be anchored to cities above a chosen population threshold and tuned to favor tighter, more compact groupings that better approximate real driving distances, rather than clusters that simply maximize point count. Each cluster is sized to fully account for the inefficient workload in a region, so the output maps directly onto a hiring decision rather than a general hotspot indicator.

Analysis Clusters — 8 clusters covering 1,913 travel inspections identified as inefficient

Future Year Analysis

  • Takes a projected increase in next year's inspection volume, scales the workload accordingly, and subtracts what the current inspector network could still cover locally. The remaining workload — what current staff could not absorb — is clustered using the same method as the current-year analysis, converting a projected growth figure into a concrete recommendation: how many hires, and where.

Future Year Analysis — projecting 2× workload growth, 18 hire regions identified

All three maps are interactive controls built directly into the dashboard's HTML — cluster radius, minimum city population, and projected workload can all be adjusted and re-clustered live in the browser, with no need to rerun the underlying Python pipeline.

Hiring Recommendation Report

  • The dashboard is paired with an Excel report that converts each identified cluster into a hiring recommendation: the estimated cost of continuing to cover the area with travel inspectors versus the cost of hiring locally, with potential savings broken out per region. It is formatted as a decision-ready document for leadership review, rather than a raw data export.

Results

$250K in projected annual savings opportunities

The initial analysis identified several geographic concentrations with sufficient travel volume to warrant evaluation for local hiring. The resulting recommendations represented approximately $250,000 in projected annual savings opportunities. The system was designed as a repeatable analysis rather than a one-time report, allowing the organization to reassess hiring needs as inspection volume and geographic coverage change.

Engineering Lessons

Reflections

  • Geocoding at scale is an engineering problem, not a data problem. A naive one-API-call-per-address approach hits rate limits within minutes on any real dataset. Batching, aggressive caching, and fallback logic for addresses that don't resolve cleanly turned a 17-minute-per-run geocoder into one that finishes in seconds on warm data.
  • Clustering algorithms need a clear contract for what the radius means, and what counts as a valid center. Early attempts produced clusters centered on empty points with no realistic hiring target nearby. Anchoring cluster centers to actual population centers made every result actionable.
  • Frontend interactivity in generated HTML needs careful scoping. Functions defined inside an IIFE are invisible to onclick= attributes, which resolve in the global scope — understanding the distinction between module-based and single-file embedded JavaScript patterns resolved the bug.
  • A rerunnable tool is worth more than a one-time analysis. A script that analyzes a snapshot of data is useful once; a tool that can be re-run on fresh data, with persistent caching and structured outputs, is useful indefinitely.
