CMCS · $250K Business Impact

Geographical Inspection Recruitment Analysis

CMCS was paying inspectors extra to travel to jobs that a local inspector could already cover, or that would have been cheaper to cover by hiring locally. I mapped and clustered those travel inspections to find exactly where hiring made sense — an analysis that hadn't been done before, and one that surfaced a $250,000 hiring opportunity in its first run.

Python Census Geocoding API Geospatial Clustering Leaflet.js openpyxl SQLite

The Problem

Paying a travel premium for coverage that already existed

CMCS inspectors are paid extra when a job requires travel outside their normal territory. Across a nationwide network of independent inspectors, a lot of that travel was avoidable — either another inspector was already working nearby, or the job volume in that area was steady enough that hiring a local inspector would have been cheaper in the long run. Nobody had systematically looked at where that was happening — CMCS didn't have the tools to run that analysis.

The Approach

Mapping and clustering travel inspections to find real hiring opportunities

I built a system that pulls in CMCS's live inspection data, geocodes every address, and classifies each inspection as local or travel relative to the inspector who worked it. From there, it clusters the travel inspections geographically to find where enough of them are concentrated to justify a new hire. The output is a single dashboard with three interactive maps, plus an Excel report ready to hand to leadership.

Ingest inspection data → Geocode → Classify (Local / Travel) → Cluster (population-aware) → Dashboard + hiring report

Technical Implementation

A three-map dashboard, plus a hiring recommendation report

Every run produces one self-contained HTML dashboard with three interactive maps, and one Excel report:

Inspector Ranges

  • Maps every inspector alongside their inspections, classifying each one by whether it required travel, whether another inspector was already working nearby when it did, and whether it's already been completed or is still planned for later in the year. This was the first time the network could be seen laid out geographically instead of buried in spreadsheets.

Inspector Ranges — 116 inspectors mapped with their inspection locations and classifications

Analysis Clusters

  • Takes every travel inspection for the year and clusters the ones that are geographically concentrated enough to represent a real inefficiency. Clusters can lock onto cities above a chosen population size, and can be tuned to favor tighter, more compact groupings — closer to real driving distances — over clusters that just contain the most points. The clustering is built to size each cluster to fully absorb the inefficient workload in a region, so it maps directly onto a hiring decision rather than just flagging a hotspot.

Analysis Clusters — 8 clusters covering 1,913 travel inspections identified as inefficient

Future Year Analysis

  • Takes a projected increase in next year's inspection volume, scales the workload accordingly, and subtracts whatever the current inspector network could still cover locally. What's left — the workload current staff can't absorb — gets clustered the same way as the current-year analysis, turning a projected growth number into a concrete answer: how many hires, and where.

Future Year Analysis — projecting 2× workload growth, 18 hire regions identified

All three maps are interactive controls built directly into the dashboard's HTML — cluster radius, minimum city population, and projected workload can all be adjusted and re-clustered live in the browser, with no need to rerun the underlying Python pipeline.

Hiring Recommendation Report

  • The dashboard is paired with an Excel report that turns each identified cluster into a hiring recommendation: the estimated cost of continuing to cover the area with travel inspectors versus the cost of hiring locally, and the potential savings, broken out per region. It's formatted to go straight to leadership as a decision-ready document, not a raw data dump.

Results

A $250K hiring decision, and an ongoing tool

The initial run surfaced a concrete, actionable insight: several geographic clusters showed high volumes of travel inspections — meaning CMCS was either paying travel premiums to send inspectors far from home, or routing work to travel inspectors in areas a local inspector could already cover. Quantifying the volume and location of that misalignment identified specific hiring targets; the projected savings from making the right hire came to approximately $250,000.

What I Learned

Reflections

  • Geocoding at scale is an engineering problem, not a data problem. The naive approach — one API call per address — hits rate limits within minutes on any real dataset. Batching, caching aggressively, and building fallback logic for addresses that don't resolve cleanly turned a 17-minute-per-run geocoder into one that finishes in seconds on warm data.
  • Clustering algorithms need a clear contract for what the radius means, and what counts as a valid center. Early attempts produced clusters centered on empty points with no realistic hiring target nearby — meaningless for the business question being asked. Locking cluster centers onto actual population centers made every result something someone could act on.
  • Frontend interactivity in generated HTML needs careful scoping. Functions defined inside an IIFE are invisible to onclick= attributes, which resolve in the global scope — a persistent bug until I understood the difference between module-based and single-file embedded JavaScript patterns, and restructured accordingly.
  • NaN in JSON fails silently. Python's json.dumps serializes float('nan') as the literal NaN, which isn't valid JSON. A browser parsing a <script> block containing it throws a SyntaxError and silently refuses to run the whole script — a blank page with no visible error unless you open the console. Sanitizing NaN/Infinity to null before serialization fixed it.
  • Forecasting needs to account for how differently inspectors behave. Applying one growth model uniformly across inspectors with very different activity levels produces numbers that are computed but not meaningful. Segmenting inspectors by activity pattern before forecasting next year's workload made the Future Year Analysis results something worth planning around.
  • There's a real difference between a one-time analysis and a rerunnable tool. A script that analyzes a snapshot of data is useful once. A tool that can be re-run in a single command on fresh data, with persistent caching and structured outputs, is useful indefinitely. This project started as the former and became the latter.
