Hathaway Brown School · Pro Bono Project · 2025

Aspire Choice Period Assignment System

A preference-driven class assignment system developed for Hathaway Brown's Aspire program. Students submit their preferences through a Google Form, and the system generates capacity-constrained assignments through an automated matching process. I led the three-person development team and served as the primary point of contact with the school throughout the project.

Google Apps Script Maximum Bipartite Matching Team Leadership Stakeholder Communication

The Problem

A recurring assignment problem managed manually

Aspire is a Hathaway Brown program that works with middle school girls in Greater Cleveland who are navigating academic hardship and working toward being the first in their families to attend college, taught in part by high school and college students under the mentorship of experienced educators. During its daily Choice Period, students select from a set of elective sessions with fixed capacity limits. Before this system was developed, a volunteer manually converted student preferences into class assignments each day. The process was time-consuming, repetitive, and susceptible to inconsistent assignments as preferences and capacities changed.

The Approach

A workflow simple enough for anyone to run

The system was designed around a simple operational requirement: staff should be able to run the entire workflow without interacting with the underlying code. Students submit preferences through a familiar Google Form, responses are captured in Google Sheets, and Apps Script validates the data, executes the matching algorithm, and generates the final assignments.

Google Form (student input) → Response sheet → Apps Script matching engine → Shared class assignments

Technical Implementation

Choosing the matching algorithm

The assignment problem can be represented as a capacitated bipartite matching problem, with students on one side and sessions on the other. An edge represents a student's ranked preference, while each session has a fixed capacity. The objective is to maximize the quality of student assignments subject to those capacity constraints, making a maximum matching formulation more appropriate than a two-sided stable-matching algorithm — sessions don't have preferences of their own, so the extra machinery a Gale-Shapley-style approach brings wasn't buying anything, and a matching algorithm was far simpler to implement correctly in Apps Script within Google's execution-time limits.

The engine processes ranked preferences using augmenting paths, allowing assignments to be reconfigured when an initially selected session is full. This prevents an earlier assignment from unnecessarily blocking a higher-priority preference for another student. The system resolves the full dataset in well under a minute and can be re-run after changes to capacities or late submissions.

Edge Cases

Designing for adversarial and incomplete input

Once students began interacting with the system, the Form had to be treated as an uncontrolled input source rather than a clean dataset. The system therefore had to account for duplicate submissions, incomplete preferences, repeated rankings, late responses, and attempts to manipulate outcomes through strategically limited preference lists — for example, listing only one "safe" choice to guarantee a seat there rather than risking a more competitive option elsewhere.

Before the system ever touched a real response, I wrote a battery of synthetic test cases that mirrored this behavior — duplicate submissions, blank and repeated rankings, late entries, capacity ties — and ran the matching engine against all of them until every case resolved to one clean, valid assignment. That testing pass caught more real problems than anything in the "happy path" version of the system would have.

Leading the Team

Delegating, tracking, and being the point of contact

I led a three-person development team, owning the matching engine and core Apps Script implementation while delegating Form and response-sheet setup and the validation-and-testing pass to the other two, with regular check-ins to track progress and unblock whichever piece was behind. I also served as the primary liaison with the school, translating informal or non-technical requirements — a grade-level priority rule, a hard cap that changed midway through the program — into concrete system specifications, and communicating implementation status and limitations back to a nontechnical stakeholder.

Rolling It Out

Designing for independent operation

The system was designed so that staff could operate it without technical assistance. I trained the program liaison and staff on submitting responses, generating assignments, re-running the process after updates, and handling exceptions manually when necessary. The final workflow required no interaction with Apps Script or other underlying implementation details.

Results

Impact

The system replaced the existing manual assignment process with a repeatable workflow that generated capacity-constrained assignments within minutes and could be re-run whenever responses or capacities changed. The system was designed to remain reliable under the incomplete and duplicate submissions encountered during actual use.

Design Lessons

Reflections

  • Independent operation should be treated as a system requirement. The final product had to be simple enough for staff to use without understanding the implementation behind it.
  • Algorithm selection should follow the objective. Modeling the problem directly as a capacitated matching problem avoided unnecessary complexity and better reflected the actual assignment requirements.
  • Real users will find every edge case a test suite misses. Designing synthetic test cases around how students would actually try to game the form caught problems no happy-path test ever surfaced.
