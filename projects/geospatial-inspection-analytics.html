CMCS · $250K Business Impact

Geospatial Inspection Analytics Platform

An end-to-end analytics platform that geocodes, classifies, and clusters a nationwide portfolio of housing inspections carried out by independent inspectors across the country — the first run directly surfaced a hiring decision worth an estimated $250,000.

The Problem

No programmatic view of a nationwide inspection network

CMCS manages thousands of HUD-regulated property inspections across the United States, carried out by a network of independent inspectors spread across the country. Before this project, there was no programmatic way to see where inspections were happening, which inspectors were covering what geography, whether assignments made geographic or logistical sense, or how to plan future hiring. All of that analysis happened manually, in spreadsheets, or not at all.

The Approach

An ingest → geocode → classify → cluster → forecast → report pipeline

I designed and built a suite of Python tools — now consolidated into a single, rerunnable system — that ingests the company's live inspection data, geocodes every address, classifies every inspection by geography and status, clusters inspections by proximity and workload, models inspector capacity, and presents all of it through interactive maps and structured Excel reports.

Technical Implementation

How it works

Data Ingestion

  • Reads directly from the company's live .xlsm workbook using pandas and openpyxl. The source sheet — Combined Insp and Prop — contains every inspection record: status codes, addresses, inspector assignments, travel flags, and duration data. All columns are preserved through the pipeline so nothing is lost.

Geocoding Pipeline

  • Two-pass batch geocoding using the US Census Bureau's free batch geocoding API — no API key, no rate limit. The first pass sends full street addresses in batches of 1,000; the second pass sends city/state/zip for anything that failed, including PO Box addresses (explicitly detected and routed to the fallback, since the Census API can't geocode those by street).
  • A persistent JSON cache resolves every previously-geocoded address instantly on future runs — only genuinely new addresses hit the network.
  • This took the geocoder from 17+ minutes per run (the original Nominatim approach, rate-limited to one request per second) to seconds once the cache is warm.
  • Every inspector's home address is geocoded and cached separately, establishing each inspector's home-base coordinate — the foundation for all range analysis.

Classification

  • Every inspection is classified into a 4×5 matrix: 4 status groups (HUD Accepted, Archived, Cancelled, Future) × 5 location buckets (Local/Own Range, Local/Other Range, Local/Remote, Travel/Overlap, Travel/Remote).
  • This directly answers the questions that matter operationally: is an inspector working their own territory? Is CMCS paying travel premiums to reach places another inspector already covers? Where are the real geographic gaps?

Clustering Algorithm

  • A centroid-refinement clustering algorithm built from scratch: it seeds each cluster on the densest unassigned point (measured by surrounding workload, not just inspection count), iteratively shifts the centroid using duration-weighted averaging until it converges, then assigns all inspections within the configured radius — enforced against the final centroid, not via chain expansion, so every cluster has a hard geometric guarantee on maximum member distance.
  • Backed by a scikit-learn BallTree for fast radius queries. The same algorithm runs both in Python (pre-computed layers) and in JavaScript (real-time "combination" clustering in the browser map).
  • Inspection duration is the weight throughout — a 4-hour inspection counts 4× a 1-hour inspection in centroids, workload totals, and seed priority, so clusters represent actual work density, not just inspection count.

Inspector Workload Forecasting

  • Each inspector is classified into one of four behavioral segments — Dormant, New, Sporadic, Established — each with its own forecasting model: Established inspectors get recency-weighted velocity with a trend adjustment; Sporadic inspectors get a blended velocity scaled by activity rate; New inspectors fall back to a team ramp curve derived from observed ramp behavior; Dormant inspectors (no completions in 6 months) are excluded entirely so they don't distort the numbers.
  • The output is a low / expected / high range per inspector, plus a pipeline utilization figure (scheduled ÷ expected completions) that immediately flags who's overbooked and who has capacity.
  • Cancelled-rate is tracked separately (cancelled ÷ total assigned), per inspector and per region.

Recruiting Automation — NSPIRE Finder

  • A companion tool that scrapes the NACHI and ASHI certification databases — the two main inspector certification bodies — for candidates potentially open to work, using Tavily as the primary search provider with DuckDuckGo as a fallback.
  • Candidates are scored by Gemini AI against fit criteria, stored in SQLite, and exported to a formatted Excel spreadsheet.
  • Targeting verified certification sources — rather than resume databases — means every surfaced candidate is already a credentialed inspector: a structural advantage over manual job-board review.

Outputs

  • Two interactive Leaflet.js maps. The analysis map has 21 pre-computed layers (one per category), a single-category mode, and a combination mode where any subset of categories can be selected and clustered dynamically in the browser — powered by a spatial grid index for O(1)-amortized neighbor lookup, so combining categories with thousands of inspections each completes in well under a second. A second map shows every inspector's home location, coverage-radius circle, and every inspection within it, color-coded by classification.
  • Excel outputs via openpyxl with full formatting — color-coded headers per status group, alternating row backgrounds per location bucket, frozen panes, conditional color-scale formatting on distance and duration columns, and cluster divider rows labeled with size, workload, and geographic center. One sheet per category, plus a summary pivot table.

Architecture — built to be rerun, not just run once

  • The original design was two separate scripts — one classifying inspections into an intermediate Excel file, a second reading that file back in to cluster it. I eliminated the intermediate file by consolidating both into a single script, combined_analysis.py: classification now runs in memory and passes DataFrames directly into clustering. The tool runs in one command and produces both outputs (Excel + HTML map) in a single pass — no manual intermediate steps, no stale files, safely re-runnable any time the source workbook refreshes.

Results

A $250K hiring decision, and an ongoing tool

The initial run surfaced a concrete, actionable insight: several geographic clusters showed high volumes of inspections classified as Travel/Remote or Travel/Overlap — meaning CMCS was either paying travel premiums to send inspectors far from home, or routing work to travel inspectors in areas a local inspector could already cover. Quantifying the volume and location of that misalignment identified specific hiring targets; the projected savings from making the right hire came to approximately $250,000.

What I Learned

Reflections

  • Geocoding at scale is an engineering problem, not a data problem. The naive approach — one API call per address — hits rate limits within minutes on any real dataset. Batching (1,000 addresses per request), caching aggressively, building multi-pass fallback logic, and detecting known-bad formats like PO Boxes before they waste a call turned a 17-minute-per-run geocoder into one that finishes in seconds on warm data.
  • Clustering algorithms need a clear contract for what the radius means. Early chain-link expansion (A near B, B near C ⇒ one cluster) produced clusters averaging 500+ miles from their center — meaningless. Replacing it with centroid-refinement clustering, where the radius is enforced against the final centroid, gives every cluster a hard geometric guarantee instead.
  • Frontend interactivity in generated HTML needs careful scoping. Functions defined inside an IIFE are invisible to onclick= attributes, which resolve in the global scope — a persistent bug until I understood the difference between module-based and single-file embedded JavaScript patterns, and restructured accordingly.
  • NaN in JSON fails silently. Python's json.dumps serializes float('nan') as the literal NaN, which isn't valid JSON. A browser parsing a <script> block containing it throws a SyntaxError and silently refuses to run the whole script — a blank page with no visible error unless you open the console. Sanitizing NaN/Infinity to null before serialization fixed it.
  • Workforce forecasting needs segment-aware models. The same velocity formula applied uniformly to a three-year veteran and an inspector active for one month produces numbers that are computed but analytically wrong. Classifying inspectors into behavioral segments first, then applying the right model per segment, generalizes well beyond this project — a metric computed uniformly across a heterogeneous population usually hides more than it reveals.
  • There's a real difference between a one-time analysis and a rerunnable tool. A script that analyzes a snapshot of data is useful once. A tool that can be re-run in a single command on fresh data, with persistent caching, robust error handling, and structured outputs, is useful indefinitely. This project started as the former and became the latter.
